# Supabase: development and deployment

## Security boundaries

The client only ever receives the project URL and a **publishable** key, generated by BuildKonfig. Never a secret key or `service_role` — on Android, iOS, or web. Data API permissions are granted explicitly, only after the RLS policies exist.

Auth uses email/password, PKCE, and the `shareat://auth-callback` redirect; web uses its own origin. Email confirmation and OAuth are out of scope for the MVP. Android declares the intent filter, iOS the URL scheme, web a CSP restricting connections and images to the app's origin and the Supabase project.

Storage has a private `avatars` bucket and public `restaurant-images`/`dish-images` buckets. All of them cap JPEG/PNG/WebP at 500 KB. Replacing an image uploads a new random path, updates the row, and only then attempts to delete the old file (never delete-then-upload).

## Local flow

```bash
npm install
npx supabase start
npx supabase db reset --local
npx supabase test db
npx supabase db lint --local --schema private,public --level warning --fail-on warning
```

Create migrations only with `npx supabase migration new <name>`. The seed is local-only and never part of deployment.

## Safe deployment

1. Run reset, pgTAP, and the local lint.
2. Review `supabase db push --dry-run` once the CLI is linked to the project.
3. Apply only the pending migrations to the development project.
4. Diff the hosted migration history against `supabase/migrations`.
5. Run smoke queries plus the security and performance advisors.

Never run a remote reset. Auth URL/redirect changes are configured in the dev environment and must include `http://localhost:8080/**` and `shareat://auth-callback`.
